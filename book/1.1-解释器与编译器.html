1.1 解释器与编译器：运行时环境的变迁

对于习惯了 Golang 编译成二进制文件或 Python 解释执行的后端开发者来说，TypeScript (TS) 的运行机制可能显得有些“不伦不类”。本节将带你厘清 TS 代码是如何跑起来的。

1. 核心概念映射

概念 TypeScript Golang Python
编译产物 JavaScript 源码 (.js) 二进制机器码 字节码 (.pyc)
运行方式 解释执行 (V8 Engine) 直接执行 解释执行 (Python VM)
类型检查时机 编译时 (Transpilation) 编译时 (Compilation) 运行时 (Type Hints 仅供参考)

2. 编译 vs 转译 (Compilation vs Transpilation)

在 Go 中，go build 会将源代码直接编译成机器码，脱离 Go 环境也能运行。 但在 TypeScript 中，tsc (TypeScript Compiler) 实际上是一个 Transpiler (转译器)。

  • Go: Source Code -> Machine Code (不可读)
  • TS: TS Code -> JS Code (人类可读)

这意味着：TypeScript 不会在运行时存在。 浏览器或 Node.js 真正执行的是被“擦除”了类型信息的 JavaScript 代码。

[思维映射] 为什么这很重要？

  • Go 开发者注意：在 TS 中，你无法在运行时检查一个变量是不是 Interface A。因为 Interface A 在编译成 JS 后就消失了。这与 Go 的 reflect 包完全不同。
  • Python 开发者注意：虽然 TS 像 Python 一样解释执行，但 TS 的类型检查是强制的（在编译阶段）。

3. V8 引擎：你的新“虚拟机”

Node.js 基于 Chrome V8 引擎。你可以把 V8 想象成一个极致优化的 Python 解释器 + JIT (Just-In-Time) 编译器。

  • 单线程模型：与 Python 的 GIL 类似，JS 也是单线程的。但它的异步模型（Event Loop）非常强大，将在第 3 章详细对比。

4. 总结

当你运行 npm run build 时，你实际上是在做类似 go generate 的工作——生成最终交付的代码（JS）。理解这一点，是掌握 TS 类型系统的第一步：类型是给编译器看的，运行时只有值的流动。
